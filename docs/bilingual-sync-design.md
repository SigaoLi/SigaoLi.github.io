# 双向内容同步 · 设计

> 2026-09-14 定稿待审。承接照片入站管线（`photo-ingest-design.md`）——同一个 pre-commit 钩子，第二条链路。

## 1. 目标

改中文还是改英文都行，**另一边自动跟上，不用指定方向**。

今天的实际状态是这条管线已经停摆：`translate.mjs` 是单向的（en→zh），且 12 个目标文件**全部**被人工改过、触发 override 保护，现在跑它一个文件都翻不动。事实上这段时间是纯人工维护双语。

## 2. 核心判定链

```
文件对（cases/x.md ↔ cases-zh/x.md）
        │
   ① 哈希比对：跟「上次同步基线」比，两边各自变了没
        │
   ├─ 都没变      → 跳过。零调用、零成本
   ├─ 只有一边变  → ② 语义判定：这个改动让对面过时了吗？
   │                   ├─ 没过时 → 不翻译。**基线不推进**（见 §4）
   │                   └─ 过时   → 翻译 → 写入 → 基线推进到两边当前
   └─ 两边都变    → 人工已做完，不调模型，基线直接推进到两边当前
```

第三条是 Sigao 定的规则：两边都改 = 人不需要 LLM 帮忙了，走后面流程即可。

它同时解掉了眼下的僵局——现在 12 对**全是**「两边都变」，新管线第一次跑会把它们全部重新基线化，**一次翻译都不发生**，这正是正确行为。

## 3. 为什么要语义判定这一层

Sigao 提出的：能不能让模型分清「润色」和「改内容」，只在真改了内容时才同步？

能。**23 个真实改动样本、两次独立运行结果完全一致**：

| 模型 | 正确 | 假阴性（危险） | 假阳性（浪费） | 均耗时 |
|---|---|---|---|---|
| **gpt-5.6-sol** | **23/23** | **0** | **0** | **1.8s** |
| gpt-5.5 | 23/23 | 0 | 0 | 2.3s |
| kimi-k2.6 | 23/23 | 0 | 0 | 3.9s |
| claude-opus-4-5 | 22/23 | 1 | 0 | 3.0s |
| gpt-5.6-terra | 21/23 | 1 | 1 | 2.0s |
| deepseek-v4-pro（原任） | 21/23 | 2 | 0 | 6.8s |

样本覆盖：纯润色（换词序 / 改标点 / 整句重写同义 / 加 `**强调**` / 补逗号）、改事实（增删论点 / 改年份 / 换技术名词 / 加限定词）、**刁钻边界**（数十→数百这种改一个字的、大段润色里藏一处数字、程度词 `无法`→`难以`、`会`→`可能`）、以及反方向（改英文判中文是否过时）。

⚠️ **评测过程中我造错过一个样本**：第 21 号中文从「相似的公司名称」改成「几乎相同」，而英文原文本就是 `near-identical`——这个改动让两边**更贴近**，英文并未过时，我把答案标反了。更正后排名整个翻转，上表是更正后的结果。

## 4. 防累积：基线记的是「译文照着哪一版译的」

判为「润色、不用翻」时**不推进基线**。否则十次各自无害的微调叠起来可能已经变了意思，却因为每次都只跟上一次比而永远触发不了。

所以缓存记的是**上次真正同步时两边的哈希**，不是上次看到的。这样偏移会累积，迟早跨过阈值。

## 5. 缓存结构要换

现在是单向的 `{srcHash, outHash}`，只能表达「英文→中文」。换成对称的，以文件对为键：

```json
"cases/csr-scraper.md": { "en": "<上次同步时英文的哈希>", "zh": "<上次同步时中文的哈希>" }
```

## 6. 模型选型

**两个任务用两个模型**——它们要求不同的能力：判定要细致的差异感知，翻译要英文语感。

| 任务 | 模型 | 理由 |
|---|---|---|
| 语义判定 | `gpt-5.6-sol` | 23/23 且两次复跑稳定、最快；假阴性是这里唯一的真风险 |
| zh→en 翻译 | `claude-opus-4-5` | 风格最贴近现有英文原文（`cookie banners` / `naive crawlers` / `validates`），用词最克制 |
| en→zh 翻译 | `deepseek-v4-pro` | **保持不动**。现有「信达雅」提示词是两轮实验选出来的，没有理由推翻 |

**成本实测**（真实文件 × 官方价）：改一个文件 $0.031，一年按每周改 2 个算 **$3.22**。最贵与最便宜的组合全年差 $2.56，12 对全量重翻也只要 $0.37。**这个量级不该作为选型依据，故按质量选。**

顺带一个发现：kimi-k2.6 单价便宜，但翻译输出 3388 token 是其他模型的 5 倍（sol 582 / opus 645），单看价目表会误判。

## 7. zh→en 提示词（新写）

现有提示词只有 en→zh。反方向从现有英文内容里挖出两条 Sigao 的惯例：

- **美式拼写**——organization / visualization / optimization 共 9 处，英式只有 1 处 `visualised`（在 cv.json 那条 bullet 里，是个漏网的不一致）
- **metrics 标签小写开头**——14 比 1，因为它接在数字后面读：「150 reports targeted across 49 companies」

加上机构通行译名表、禁 AI 套话（leveraged / cutting-edge / seamlessly）、不可译字段清单。

**实测 13 项机械核验**（不可译字段原样、数字准确、模型名 DeepSeek-R1 8B / Qwen2.5-VL 3B 保留、拼写、小写惯例、无代码围栏）：五个候选模型**全部 13/13**。说明提示词到位后这个任务对强模型不难，差别只在风格。

## 8. 粒度

- **CV（结构化 JSON）**：分区处理，见下表
- **Markdown**：整文件判定

### cv.json 各区的处理方式（实测确认）

| 区 | 有 id？ | 处理 |
|---|---|---|
| `current` `education` `experience` `research` `volunteering` | ✅ | 按 `id` 逐条判定 |
| `awards`（7 条）`certifications`（2 条） | ❌ | 按**数组下标**成对判定——实测中英下标严格对齐（awards 的 year 逐条相符，certifications 的 org 一一对应） |
| **`skills`** | ❌ | **绝不同步**。中英**结构本就不同**：en 是 `{data, frameworks, tools}` 对象，zh 是数组——这是 PRD v2.3 的**有意设计**（渲染层兼容两形态）。强行同步会破坏页面 |
| `_note` | — | 跳过。是英文元数据备注，中英本就一字不差，不该翻译 |

**CV 的条目级判定要处理三种结构变化**，不只是「同一条改了」：

| 情况 | 处理 |
|---|---|
| 某 `id` 两边都在，内容变了 | 走 §2 判定链 |
| 某 `id` **只在一边**（新增了一段经历） | 直接翻译补到对面，无需语义判定——对面根本没有，谈不上过时 |
| 某 `id` 在一边被**删了** | **同步删掉对面那条**。Sigao 定：人为删掉就是要它消失，不必报错阻断 |

删除同样走「每个改动独立落地」，且删的是 git 已追踪的内容——真删错了，`git diff` 当场就能看见，提交前还能撤。

不做节级拆分：实测三篇案例的 `## Challenge/Approach/Impact` 中英确实一一对应，本可以做——但**语义判定已经解决了「小改动不该重写全文」这个问题**，再拆是多余复杂度。

## 9. 范围

现有 12 对：5 篇案例、6 个研究方向、CV。

**新增文件**（比如写了第 6 篇案例）：只有一边存在时，直接翻译生成对面，无需语义判定。这和 CV 的「某 id 只在一边」是同一条规则。

**删除文件**：一边被删而对面还在 → 同步删掉对面，与 CV 条目删除同理。⚠️ 但**只在该文件对已进过缓存基线时**才这么做——否则一个还没被管线认识过的新文件，会被误判成「对面被删了」而把刚写好的另一边删掉。没有基线记录的单边文件一律当作「新增」处理。

**frontmatter 的不可译字段**（`year` / `role` / `tags` / `repoUrl` / `featured` / `order` / `metrics` 的 `value`）由提示词约束保留，并在写盘前**机械校验**——§7 那 13 项核验就是为此准备的，不通过则视为翻译失败、走重试。这是不设人工复核的前提：可机械验的部分必须真的机械验，不能只靠模型自觉。

**不进**：
- `src/lib/i18n.ts` — 手写双语，Sigao 定过不走机翻
- `src/data/knowledge/*.md` — 只有中文，做英文层是**新内容**不是同步，该单独立项（PRD v2.9 已记为积压）

## 10. 触发与失败处理

pre-commit 钩子，与照片链路并列。沿用照片管线的成熟做法：

- 无改动文件 → 立即退出，日常提交零开销
- 退避重试 3 次（1s / 4s / 9s）
- 三次仍失败 → 打印卡在哪个文件哪一步 → 非零退出 → **commit 被阻断**
- **每个文件独立落地**：写盘 → `git add` → 才推进基线。不攒批（照片管线吃过这个亏，见 `photo-ingest-design.md` §6）

## 11. 不设人工复核

Sigao 定：调研做扎实就不需要人工再审一遍。本设计的调研依据即 §3 与 §7 的两组实测。

## 12. 已知风险

- **程度词的细微改动可能漏判**。`无法`→`难以` 这类，sol 在 23 样本里没漏，但这是 §3 里多数模型的共同失手点，样本量有限。后果是英文保持原样而非悄悄写错——可接受，且 §4 的防累积机制让它迟早会被下一次改动带出来。
- **网关加价率未知**。取不到 NewAPI 的计价接口（要管理员令牌），§6 的成本是官方价下限估算，量级不会变。
- 两个模型意味着两条链路要各自处理失败。
