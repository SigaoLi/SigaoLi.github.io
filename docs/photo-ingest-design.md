# 照片入站自动化 · 设计

> 2026-09-13 定稿待审。本阶段**只做照片**；其他内容更新路径（案例研究翻译、CV、UI 文案、Zoe 语料与素材）留到下一阶段单独讨论。

## 1. 目标

把加照片这件事从九步手工操作压缩成一步：**把原图丢进 `_inbox/`，照常 `git commit`。**

今天的手工流程（2026-09-12 加两张图时实际走了一遍）：归档原图 → 派生母版 → 读 GPS → 判断国家 → 看图写中英文案 → 插 `photos.json` → 改 README 计数 → 改 `verify-facts.mjs` 计数 → 构建验证。

## 2. 已定决策

| # | 决策 | 理由 |
|---|---|---|
| 1 | **全自动，不设人工复核闸门** | Sigao 定。已知代价见 §9 风险 |
| 2 | **pre-commit 钩子触发**，不是 push | 产物必须并入本次提交 |
| 3 | **本地生成 / CI 验证 两层分工** | 原图不在 git 里，CI 拿不到；生成类只能在本地 |
| 4 | **文案用 claude-opus-4-5 单模型** | 实测 2/2 正确，唯一认出厦门双子塔的 |
| 5 | **失败退避重试 3 次，仍失败则阻断提交** | 网关有 504 与瞬时断连历史 |
| 6 | **收件箱 = 仓库根 `_inbox/`**，gitignore | 一眼可见，残余不会被忽略 |

**国家判定不用模型**：EXIF 坐标 + `world-atlas/countries-10m.json` 国界多边形，`d3-geo` 的 `geoContains` 做几何包含判断。两者都已是项目依赖（画地图点阵时在用）。确定性运算，无幻觉风险。VLM 只负责写文案。

**但原始数据有两个坑，实测发现，必须处理**（用现有 78 条真实坐标验证）：

1. **`countries-10m.json` 里 Maldives 的多边形环绕方向是反的**，`geoContains` 判它覆盖几乎全球——北京、多伦多、京都全都会额外命中它。实测它是 255 个国家里**唯一**有此问题的，拉进黑名单即可。
2. **两成照片落在陆地多边形之外。** 78 张里有 16 张判不出国家，全是海岸/水上取景：纽约港、迈阿密海滩、金门大桥、圣莫尼卡、拿骚、侏罗纪海岸、福斯桥、厦门海滨、北戴河…… 旅行照片本来就常在岸边拍，加上坐标四舍五入到 1 位小数（约 11km）会把临海点推到海里。

**解法：黑名单 + 向外扩圈兜底。** 直接命中则采用；无命中则以 0.1° / 0.25° / 0.5° / 1° 为半径各采样 16 个方位（经度按 `cos(纬度)` 收缩以近似等距，四圈约 11 / 28 / 56 / 111 km），取命中最多的国家。

**扩圈用的是陆地国界，不是领海/EEZ。** 语义是"这张照片离哪国的陆地最近"，不是"落在谁的领海里"。领海方案需要另引入 EEZ 边界数据集（数十 MB），而对旅行照片来说"最近的陆地"语义反而更准——海滩、桥上、渡轮上拍的本就归岸上那个国家。已知局限：窄海峡正中（英吉利海峡、直布罗陀）可能归错，走手动通道兜底。

**黑名单的已知代价**：马尔代夫本身从此判不出国家（它的多边形被整个排除，扩圈时周围又全是印度洋）。现有 6 国不含它；将来去了走手动通道 `_inbox/maldives/`。

**实测结果：78/78 全部正确，零误判、零歧义**，16 张海岸照片全部在第一圈（0.1°）解决，且没有任何一张同时命中两个国家。注意这是拿**四舍五入后**的坐标测的，比真实管线（读原图全精度 EXIF）更严苛。

## 3. 数据流

```
_inbox/IMG_xxx.jpg                        ← 你丢进来的原图（gitignore，只在本机）
      │
      ├──→ _originals/photos/<国家>/IMG_xxx.jpg     全分辨率，EXIF 完整，gitignore
      │                                              底片库，将来重导其他尺寸靠它
      │
      └──→ src/assets/photos/<国家>/IMG_xxx.jpg     2560px / q82 / mozjpeg，EXIF 剥光
                                                     进 git，站点构建用这份
      处理完从 _inbox/ 删除
```

两级结构是现有设计（`compress-photos.mjs` 当初定的），本设计沿用，不改变。

## 4. 钩子流程

**第 0 步：`_inbox/` 为空则立即退出**，commit 照常走。日常改代码的提交零开销。

非空时，逐张处理：

| 步 | 动作 | 细节 |
|---|---|---|
| 1 | 读 EXIF | GPS 坐标、`DateTimeOriginal` |
| 2 | 判定国家 | `geoContains(countries-10m, [lng, lat])` |
| 3 | 归档原图 | → `_originals/photos/<id>/`，目录按需创建 |
| 4 | 派生母版 | `rotate()` 烘焙方向 → 长边 >2560 则缩放 → `jpeg({quality:82, mozjpeg:true})`，sharp 默认剥除全部元数据 |
| 5 | VLM 写文案 | 见 §5 |
| 6 | 登记 | 按**拍摄时间**插入 `photos.json` 对应国家的 `items` 正确位置（见下方排序注意） |
| 7 | 清理 | 从 `_inbox/` 删除该文件 |

全部处理完：

| 步 | 动作 |
|---|---|
| 8 | 同步计数（见 §7） |
| 9 | `git add` 所有产物，并入本次提交 |

### 排序注意：不能按文件名排

`photos.json` 现有条目是**按拍摄时间**排列的，而文件名有两种历史格式并存：`IMG_20170731_154353.jpg`（带下划线）与 `IMG20260905155409.jpg`（不带）。ASCII 里 `_`(95) 大于数字(48–57)，所以纯文件名字典序会把 2017 年的排到 2026 年之后——与现有顺序相反。

排序键取 EXIF `DateTimeOriginal`，回退到文件名中解析出的日期串。

**已验证**：78 条现有记录的文件名全部能解析出日期（正则 `/(20\d{2})_?(\d{2})_?(\d{2})/`），且 6 个国家的现有排列顺序**都等于日期升序**——所以按解析日期插入与现状完全一致，不会打乱既有顺序。

### 国家 id 映射

Natural Earth 的英文国名 → `photos.json` 的 `id`。规范化规则：小写、空格转下划线、去掉冠词。纯机械变换覆盖不了的走例外表：

```
"United States of America" → united_states
"The Bahamas"              → bahamas
```

现有 id：`china` `japan` `canada` `united_states` `united_kingdom` `bahamas`。

### 没去过的国家

自动新建条目追加到 `photos.json` 末尾（= 画廊顺序末尾）：
- `name` 取 Natural Earth 英文名
- `nameZh` 由 opus 翻译
- `lat` / `lng` 取该国多边形质心（用于画廊标题行的 `35.0° N, 104.0° E` 显示）

### 没有 GPS 的照片

无坐标则无法判定国家、也上不了地图。手动通道：丢进以**国家 id** 命名的子目录（如 `_inbox/china/`、`_inbox/united_kingdom/`）即强制归到该国，坐标留空。站点本就支持无坐标条目（`LensPage.astro` 的地图只渲染 `typeof lat === 'number'` 的项）。

## 5. 文案生成

**输入**：1024px JPEG + GPS 坐标 + 拍摄时间 + **同国已有的 3–5 条 `alt`/`altZh` 作为 few-shot 样例**（保持语感一致，这是文案不跑偏的关键）。新国家没有同国样例时，改取全站最近登记的 5 条。

**输出** JSON：`{ alt, altZh, city, cityZh }`

**约束**：
- 只描述画面中真实可见的内容；认不出具体地点就不要点名
- 中文不是英文的直译，各自成句
- **`city` 必须是单个城市名**——实测 opus 会输出 `"Xiamen, Fujian"`，需在 schema 约束基础上再做后处理截断
- 文风对齐 `src/data/photos.json` 现有 78 条（简短、具体、不用句号）

**重试**：退避 3 次（1s / 4s / 9s）。

## 6. 错误处理与幂等

- **每张图独立落地**：登记进 `photos.json` 并写盘、`git add` 之后，才从 `_inbox/` 删除。
- 失败的那张图**自动撤销自己的派生物**（归档件 + 母版），留在收件箱里等重跑。
- 目标文件名已存在 → 报错阻断（不静默覆盖）。
- 三次重试仍失败 → 打印卡在哪张图的哪一步 → 非零退出 → **commit 被阻断**，仓库不会留下半成品。

**这两条是实跑失败路径后改的，原设计有两个连锁 bug**（已修，见 commit `f1b57a0`）：

1. 派生物在请求文案**之前**就落盘了。文案失败时，归档件和母版留在磁盘上而图还在收件箱——重跑会撞进 `archiveAndDerive` 的「已存在」并**永久卡死**，除非手工去两个目录删文件，其中一个还是 gitignore 的、根本不会想到去翻。
2. 更严重：`photos.json` 原本攒到整批结束才写，但每张图一成功就离开收件箱。第 1 张成功、第 2 张失败时，**第 1 张凭空消失**——文件在磁盘上、哪里都没登记、收件箱里也没有了，无从重试。

⚠️ **第 2 条在别处复发过**（2026-09-15 审计发现）：双语同步的 CV 条目级分支写成了同样的攒批形态——逐条翻译累积到内存、最后一次写盘，第 5 条失败则前 4 条的翻译白花。**修好一个坑之后要回头找「还有哪里是同一个形状」**，这正是 v2.38 系统性审计总结的方法，而修照片管线时我没用上。

## 9. 模块划分

```
scripts/
  ingest.mjs              编排器：查收件箱 → 串各步 → 汇总 → 退出码
  ingest/
    country.mjs           坐标 → 国家名 / id / 质心（黑名单 + 扩圈兜底）。纯函数
    photo-meta.mjs        文件名 / EXIF → 拍摄时间戳。纯函数
    intake.mjs            列收件箱 / 读 EXIF / 归档 / 派生母版。唯一碰文件系统的模块
    caption.mjs           opus-4-5 写文案与译新国家名（退避重试、JSON 校验、city 规范化）
    register.mjs          写 photos.json（插入排序、新国家建条目、幂等）。纯函数
    counts.mjs            同步 README 计数。纯函数
.githooks/pre-commit      调用 ingest.mjs（用 git config core.hooksPath 指向，随仓库版本化）
```

六个模块各自可独立运行与测试，编排器只负责串联。四个纯函数模块（country / photo-meta / register / counts）测试时不需要网络与文件系统；`caption` 的 `fetch` 由参数注入；只有 `intake` 真正读写磁盘。测试用 Node 内置的 `node --test`，不引入新依赖。

## 10. 明确不做

网页上传界面、废片筛选、美学评分、覆纱图自动生成（velatura 是独立探索，未上线）、CI 验证层（本阶段搁置）。

## 11. 风险

- **单模型无闸门，错误会直接上线并进入 Zoe 语料。** opus 在 2 张样本上全对，但 n=2 不构成保证。失败模式不是"写得差"而是"写得像模像样但错了"——对照组 gpt-5.6-terra 把厦门双子塔看成摩天轮并自评置信度 0.96。**模型自评的 confidence 不可用作放行依据。**
- `city` 字段需要后处理约束，实测 opus 会附加省份。
- 钩子被 `--no-verify` 或不走钩子的 GUI 客户端跳过时，管线不生效——但因收件箱在 git 之外，最坏结果只是照片没上站，不会污染仓库。
